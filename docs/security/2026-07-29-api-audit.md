# API Security Audit — Listae

**Date:** 2026-07-29  
**Scope:** Server Actions (`src/app/actions/`), inline Server Actions, NextAuth route (`src/app/api/auth/`), and server-side mutation/read paths invoked from pages  
**Standard:** OWASP API Security Top 10 (2023)  
**Auth model:** NextAuth v5 (database sessions, magic-link email via Nodemailer)  
**Tenancy model:** Single-user data isolation — list entries and profile themes keyed by `userId`; works catalog is global/shared

---

## Executive Summary

Listae’s mutation surface is almost entirely **Next.js Server Actions** plus a single **NextAuth catch-all route**. Object-level authorization on user-owned resources (list entries, profile themes, locale/username) is **generally sound**: mutations resolve the actor from the session and scope database writes with `userId` or `email`, not client-supplied owner IDs.

The highest-risk gaps are **unrestricted resource consumption (API4)** and **sensitive-flow automation (API6)**: no rate limiting on magic-link auth, unauthenticated catalog search that fans out to TMDB/OpenLibrary, and authenticated catalog-import/manual-work creation without quotas. Secondary gaps include missing **server-side input bounds** (notes length, search query length, `coverUrl` scheme validation) and **security misconfiguration (API8)** — empty `next.config.ts`, no runtime `AUTH_SECRET` enforcement.

**BOLA/BFLA:** No confirmed broken object- or function-level authorization on audited mutations. **Mass assignment:** Field handling is mostly explicit whitelists; `importHitAction` correctly ignores forged catalog metadata (covered by tests). **CSRF:** Server Actions inherit Next.js origin checks; NextAuth handles auth CSRF tokens — no additional custom CSRF layer found (acceptable for this stack when cookies are `SameSite`).

## Findings

### High

#### [HIGH] API4: No rate limiting on magic-link authentication

**Endpoint:** `POST` (Server Action) login form → `signIn("nodemailer")`; `POST /api/auth/*`  
**Handler:** `src/app/[locale]/login/page.tsx:65-71`, `src/app/api/auth/[...nextauth]/route.ts:3`  
**CWE:** CWE-770 (Allocation of Resources Without Limits or Throttling)

**Description:** Magic-link sign-in accepts unbounded requests with no per-IP or per-email throttling. An attacker can trigger large volumes of verification emails (harassment, SMTP cost, provider blocklisting) or probe addresses at scale.

**Evidence:**

```65:71:src/app/[locale]/login/page.tsx
          action={async (formData) => {
            "use server";

            await signIn("nodemailer", {
              email: formData.get("email"),
              callbackUrl: localePath(locale, "/library"),
            });
```

No rate-limit middleware, Upstash, or NextAuth rate-limit config exists (`src/middleware.ts` handles locale redirects only; `src/lib/auth/config.ts` has no rate-limit settings).

**Remediation:** Add per-IP and per-email rate limits on `/api/auth/*` (edge/WAF or `@upstash/ratelimit`), e.g. 5 requests / 15 min per email, 20 / hour per IP. Return generic 429 without revealing whether the email exists.

**Verification:** In a staging environment, send 10+ magic-link requests for the same email within one minute; expect HTTP 429 before email #6.

#### [HIGH] API4: Unauthenticated catalog search proxies to paid/third-party APIs without limits

**Endpoint:** `GET /{locale}?q=…&type=…` (RSC server render)  
**Handler:** `src/app/[locale]/page.tsx:38`, `src/lib/catalog/search.ts:32-87`  
**CWE:** CWE-770

**Description:** Any anonymous visitor can drive TMDB and Open Library API calls by crafting search URLs. Queries are cached (30 min TTL) but cache keys are attacker-controlled; novel queries bypass cache. No query-length cap or request-rate limit.

**Evidence:**

```36:38:src/app/[locale]/page.tsx
  const query = sp.q?.trim() ?? "";
  const type = validType(sp.type);
  const results = query ? await searchCatalog(query, type, locale) : [];
```

```58:64:src/lib/catalog/search.ts
  const searches: Promise<CatalogHit[]>[] = [];
  if (["all", "anime", "series", "movie"].includes(typeFilter)) {
    searches.push(searchTmdb(normalizedQuery, typeFilter, locale));
  }
  if (["all", "book", "manga", "comic"].includes(typeFilter)) {
    searches.push(searchOpenLibrary(normalizedQuery, typeFilter));
  }
```

**Remediation:** Require authentication for search, or add IP rate limiting + max query length (e.g. 100 chars) + global daily TMDB quota. Consider deferring provider calls to an authenticated Server Action.

**Verification:** Unauthenticated client sends 50 unique `?q=` values in one minute; observe 429 or auth redirect before provider quota is exhausted.

### Medium

#### [MEDIUM] API4: Catalog import actions lack per-user rate limits and trigger upstream fetches

**Endpoint:** Server Action `importHitAction`  
**Handler:** `src/app/actions/works.ts:37-51`, `src/lib/catalog/works.ts:77-99`  
**CWE:** CWE-770

**Description:** Any authenticated user can invoke `importHitAction` repeatedly. Each call may trigger `resolveCatalogHit` (TMDB/Open Library HTTP) before upserting into the shared `works` table.

**Evidence:**

```37:49:src/app/actions/works.ts
export async function importHitAction(formData: FormData): Promise<never> {
  await requireAuthenticatedUser();
  // ...
  const work = await importWork(source, externalId);
```

**Remediation:** Per-user rate limit (e.g. 30 imports/hour) and short-circuit when work already exists without re-fetching metadata.

**Verification:** Authenticated session submits 50 import forms in one minute; expect 429 after configured threshold.

#### [MEDIUM] API6: Unrestricted catalog pollution via manual work and import actions

**Endpoint:** Server Actions `createManualWorkAction`, `importHitAction`  
**Handler:** `src/app/actions/works.ts:54-71`, `src/lib/catalog/works.ts:143-168`  
**CWE:** CWE-799 (Improper Control of Interaction Frequency)

**Description:** The `works` table is global. Any logged-in user can create unlimited manual titles or import catalog rows with no moderation, CAPTCHA, or ownership model — enabling spam/garbage catalog entries that appear on title pages for all users.

**Evidence:**

```143:168:src/lib/catalog/works.ts
export async function createManualWork(
  input: ManualWorkInput,
): Promise<{ id: string }> {
  // ...
  db.insert(works)
    .values({
      id,
      type: input.type,
      title,
      // ...
      externalSource: "manual",
```

**Remediation:** Tie manual works to `createdByUserId`, require admin flag for global catalog writes, or queue submissions for review. Add per-user creation quotas.

**Verification:** Single test account creates 100 manual works; observe quota enforcement or ownership scoping.

#### [MEDIUM] API4: Title page view triggers uncached upstream catalog fetch (`fillMissingWorkLocale`)

**Endpoint:** `GET /{locale}/title/{id}` (RSC)  
**Handler:** `src/app/[locale]/title/[id]/page.tsx:41-50`, `src/lib/catalog/works.ts:102-140`  
**CWE:** CWE-770

**Description:** On each title-page render where locale-specific text is missing, the server calls `fillMissingWorkLocale`, which invokes `resolveCatalogHit` against external APIs. Repeated page loads (or distributed requests) amplify provider usage.

**Evidence:**

```41:50:src/app/[locale]/title/[id]/page.tsx
  const missingLocaleText =
    locale === "es" ? !work.titleEs?.trim() : !work.titleEn?.trim();
  if (missingLocaleText) {
    const filled = await fillMissingWorkLocale(work.id, locale);
```

**Remediation:** Background job or one-time migration for locale backfill; guard with “already attempted” flag or rate limit per `workId`.

**Verification:** Reload a title with missing locale text 20 times; confirm at most one upstream fetch occurs.

#### [MEDIUM] API3: `coverUrl` accepted without server-side URL scheme validation

**Endpoint:** Server Action `createManualWorkAction`  
**Handler:** `src/app/actions/works.ts:63`, `src/components/work-cover.tsx:14-18`  
**CWE:** CWE-20 (Improper Input Validation)

**Description:** Manual work creation stores client-supplied `coverUrl` verbatim. The main app renders it in `<img src={src}>` without https-only filtering (unlike profile theme rendering, which uses `safeCoverUrl`). Attackers can inject non-https URLs, tracker pixels, or oversized resources affecting viewers.

**Evidence:**

```63:63:src/app/actions/works.ts
    coverUrl: String(formData.get("coverUrl") ?? "").trim() || undefined,
```

```14:18:src/components/work-cover.tsx
      {src ? (
        <img
          className="h-full w-full object-cover"
          src={src}
```

Profile theme path validates https-only at `src/lib/theme/placeholders.ts:63-73`.

**Remediation:** Validate `coverUrl` server-side: parse with `URL`, require `https:` protocol, optional hostname allow-list; reject others.

**Verification:** Submit `coverUrl=javascript:alert(1)` and `coverUrl=http://tracker.example/pixel.gif`; observe rejection or sanitization to null.

#### [MEDIUM] API4: `notes` field has no server-side length bound

**Endpoint:** Server Actions `addToList`, `updateEntry`  
**Handler:** `src/lib/lists/entries.ts:91`, `src/components/entry-form.tsx:178`  
**CWE:** CWE-770

**Description:** Client textarea sets `maxLength={500}`, but `normalizeEntryInput` accepts arbitrary-length `notes` strings. Direct Server Action invocation can store multi-megabyte notes per entry.

**Evidence:**

```91:91:src/lib/lists/entries.ts
    notes: String(input.notes ?? "").trim() || null,
```

**Remediation:** Enforce `notes.length <= 500` (or lower) in `normalizeEntryInput` and reject oversized input.

**Verification:** POST Server Action with 10 KB notes payload; expect validation error, not DB insert.

#### [MEDIUM] API2 / API8: `AUTH_SECRET` not enforced at startup

**Endpoint:** All session/crypto operations via NextAuth  
**Handler:** `src/lib/auth/index.ts:1-5`, `src/lib/auth/config.ts:17`  
**CWE:** CWE-1392 (Use of Default Credentials)

**Description:** Application boot does not assert `process.env.AUTH_SECRET` is set. Deploying without a strong secret weakens session signing and magic-link token integrity.

**Evidence:** No guard in `src/lib/auth/index.ts` or `config.ts`; `.env.example` documents the variable but runtime does not require it.

**Remediation:**

```typescript
if (!process.env.AUTH_SECRET) {
  throw new Error("AUTH_SECRET must be set");
}
```

Add at module load in `src/lib/auth/config.ts`.

**Verification:** Start app with empty `AUTH_SECRET`; expect immediate crash in production build, not silent weak defaults.

### Low

#### [LOW] API8: No security headers configured

**Endpoint:** All HTTP responses  
**Handler:** `next.config.ts:3-5`  
**CWE:** CWE-16 (Configuration)

**Description:** `next.config.ts` is empty — no `headers()` for HSTS, `X-Frame-Options`, `X-Content-Type-Options`, or CSP. Increases clickjacking and MIME-sniffing risk on non-sandboxed pages.

**Evidence:**

```3:5:next.config.ts
const nextConfig: NextConfig = {
  /* config options here */
};
```

**Remediation:** Add `headers()` in `next.config.ts` with HSTS (production), `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, baseline CSP.

**Verification:** `curl -I https://staging/listae` shows expected security headers.

#### [LOW] API8: Magic links logged to console when `EMAIL_SERVER` unset

**Endpoint:** NextAuth Nodemailer provider  
**Handler:** `src/lib/auth/config.ts:39-41`  
**CWE:** CWE-532 (Insertion of Sensitive Information into Log File)

**Description:** In environments without SMTP configured, full magic-link URLs (containing secrets) are written to stdout. Risk in shared logging pipelines if dev config reaches staging.

**Evidence:**

```39:41:src/lib/auth/config.ts
        if (!process.env.EMAIL_SERVER) {
          console.log(`[listae magic link] ${identifier} -> ${url}`);
          return;
```

**Remediation:** Gate console logging on `NODE_ENV !== "production"`; never log full URLs in production.

**Verification:** Production deploy without `EMAIL_SERVER` must fail closed or omit token from logs.

#### [INFO] CSRF: Server Actions rely on framework origin validation

Next.js Server Actions reject cross-origin posts when `Origin`/`Host` mismatch (default). NextAuth issues CSRF tokens for auth routes. No custom CSRF tokens on forms. Acceptable when session cookies use `SameSite=Lax`/`Strict` and `Secure` in production — verify NextAuth cookie defaults in deployment.

## Positive Controls Observed

- Database session strategy (`session: { strategy: "database" }`) — server-side session revocation possible
- Redirect callback blocks open redirects to external origins (`src/lib/auth/config.ts:70-78`)
- `safeReturnPath` whitelists internal locale paths (`src/lib/safe-return-path.ts:7-25`)
- External catalog IDs validated before fetch (`src/lib/catalog/openlibrary.ts:162`, `src/lib/catalog/tmdb.ts:198`)
- Profile public HTML escapes user content and restricts cover URLs to https (`src/lib/theme/placeholders.ts:36-74`)
- Theme HTML sanitized; profile iframe uses `sandbox=""` (`src/app/u/[username]/page.tsx:76-77`)
- Public profiles expose curated `ProfileEntry` DTO — **notes and email not included**

---

## Recommended Priority

1. Rate-limit magic-link auth and catalog search (High)
2. Enforce `AUTH_SECRET` at boot (Medium)
3. Add per-user quotas on catalog import/manual create (Medium)
4. Server-side bounds: notes length, search query length, coverUrl https validation (Medium/Low)
5. Security headers in `next.config.ts` (Low)
